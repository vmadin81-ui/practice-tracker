# AGENTS.md

## О проекте

`practice-tracker` — система цифрового мониторинга профессиональной практики студентов колледжа.

## Структура и технологии

### Backend

- Backend реализован на FastAPI.
- Для работы с данными используется SQLAlchemy.
- Основная СУБД — PostgreSQL.
- Миграции управляются через Alembic.
- Исходный код backend находится в `app/`.

### Frontend

- Frontend реализован на React и TypeScript.
- Сборка и локальная разработка выполняются через Vite.
- Для загрузки данных и управления серверным состоянием используется TanStack React Query.
- Исходный код frontend находится в `frontend/src/`.

## Бизнес-логика системы

Система предназначена для контроля прохождения профессиональной практики студентов колледжа на предприятиях.

Основные сущности:

- `Specialty` — специальность.
- `StudyGroup` — учебная группа.
- `Student` — студент.
- `Enterprise` — предприятие.
- `PracticeAssignment` — назначение студента на практику.
- `GeolocationLog` — запись геолокационной отметки.
- `GeolocationCheck` — результат проверки отметки.
- `StudentDailyStatus` — ежедневный статус студента.
- `StudentAccessLink` — ссылка доступа студента.
- `StudentCheckinSession` — временная сессия регистрации.
- `StudentDataConsent` — согласие на обработку геоданных.

Регистрация присутствия предусматривает:

- проверку активного назначения студента;
- определение расстояния до предприятия;
- проверку допустимого радиуса;
- проверку точности геолокации;
- учёт временного окна регистрации;
- сохранение результата проверки.

Текущее предусмотренное временное окно регистрации: 09:00–12:00.

Существующие статусы:

- `green` — успешная регистрация;
- `yellow` — регистрация с замечаниями;
- `red` — нарушение условий или отсутствие регистрации;
- `gray` — отсутствие активного назначения либо иное предусмотренное системой неактивное состояние.

Перед изменением алгоритма статусов необходимо изучить фактическую реализацию и согласовать новые правила. Не считать приведённые описания полным формальным определением алгоритма.

1. Перед изменением кода изучай все связанные части реализации:
   - модели;
   - Pydantic-схемы и TypeScript-типы;
   - CRUD-операции;
   - сервисы;
   - API-маршруты и API-клиенты;
   - React hooks;
   - страницы и компоненты.

2. Сохраняй существующие архитектурные решения, контракты API и бизнес-логику, если задача явно не требует их изменения.

3. Перед существенными изменениями предоставляй план работ с перечнем файлов, которые предполагается изменить.

4. Не изменяй без отдельного согласования:
   - существующие миграции;
   - структуру базы данных;
   - механизмы авторизации;
   - роли и права доступа;
   - правила проверки геолокации;
   - правила расчёта ежедневных статусов студентов.

5. Не выполняй команды, которые создают, изменяют или удаляют рабочие данные.

6. Не подключайся к производственной базе данных.

7. Не читай и не выводи содержимое `.env` или других файлов с секретами.

8. Не раскрывай в ответах, логах и результатах команд:
   - персональные данные студентов;
   - токены доступа и сессий;

   - точные координаты студентов;
   - другие чувствительные данные.

9. Не устанавливай и не обновляй зависимости без отдельного согласования.

10. Не выполняй `git commit`, `git push`, публикацию или развёртывание без отдельного разрешения.

## Особенности разработки

1. Для работы с датами использовать единую временную зону, установленную в проекте. Не заменять её без согласования.
2. Не изменять правила расчёта географического расстояния без проверки существующих тестов и бизнес-требований.
3. Не изменять существующие API-контракты без анализа всех зависимых frontend-компонентов.
4. Для новых функций по возможности использовать существующие архитектурные слои: models, schemas, crud, services, endpoints.
5. Для frontend использовать существующую структуру API-клиентов, React Query hooks, страниц и компонентов.
6. Не дублировать бизнес-логику между frontend и backend.
7. Не менять исторические записи геолокации и рассчитанные статусы без отдельного разрешения.

## Правила тестирования

При изменении бизнес-логики предусматривать тесты для:

- корректной регистрации присутствия;
- проверки допустимого радиуса предприятия;
- обработки недостаточной точности геолокации;
- регистрации до, внутри и после разрешённого временного окна;
- отсутствия активного назначения;
- повторных отметок одного студента;
- пересчёта ежедневных статусов;
- разграничения прав доступа.

Использовать тестовые данные без реальных персональных данных студентов.

Перед запуском тестов убедиться, что они не изменяют рабочую базу данных. При отсутствии безопасного тестового окружения сначала предложить план его создания.

2. Предлагать техническое решение с указанием затрагиваемых файлов.
3. Не приступать к реализации до согласования плана.
4. После реализации объяснять внесённые изменения.
5. Не выполнять дополнительные улучшения, не относящиеся к согласованной задаче.

После внесения изменений сообщай:

- какие файлы были изменены;
- краткое содержание изменений;
- какие проверки, тесты или статический анализ были выполнены;
- результаты выполненных проверок;
- какие проверки не удалось выполнить и по какой причине.

Не заявляй об успешности проверки, если соответствующая команда или тест фактически не выполнялись.
